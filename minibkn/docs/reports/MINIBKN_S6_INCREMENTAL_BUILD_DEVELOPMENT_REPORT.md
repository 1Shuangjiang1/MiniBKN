# MiniBKN S6 增量构建产品开发报告

> 完成日期：2026-08-16\
> 前置报告：[S5 风险 DSL 与动作门禁产品开发报告](MINIBKN_S5_RISK_DSL_DEVELOPMENT_REPORT.md)\
> 对应计划：[分步开发计划](../plans/MINIBKN_STEPWISE_DEVELOPMENT_PLAN.md)\
> 状态：已完成

## 1. 与 S5 的衔接

S5 把风险规则和动作门禁保存在已发布的 KnowledgeNetwork 中。S6 没有另建一套在线配置，而是在当前网络版本内更新业务实例、关系和检索文档，因此动作执行与风险模拟仍然读取同一份已发布规则。构建失败时会恢复原图、原索引和原索引清单，不会把半成品暴露给问答或动作链路。

## 2. 本阶段解决的问题

过去每次数据变化都要删除并重写整张图，再给所有内容重新生成向量。现在系统会比较“数据库中已经发布的数据”和“本次从源文件读到的数据”，只处理真正发生变化的部分。

例如 CRM 中修改一个订单并新增一个订单时：

- 原有 7 条业务对象中只新增 1 条、更新 1 条；
- 只新增这条订单带来的 1 条客户关系；
- 只重写 2 条检索文档并生成 2 个向量；
- 其他客户、订单、关系和向量保持不动。

## 3. 已完成能力

- 为对象内容生成稳定指纹，形成 inserted、updated、deleted 变更集；
- 比较关系三元组，只增删发生变化的关系；
- 比较检索文档内容与元数据，只对新增和更新文档调用 Embedding；
- Embedding 模型版本或维度变化时自动转为完整索引重建；
- 持久化 BuildJob 状态与对象、关系、索引、向量计数；
- 支持无变化构建，结果为零写入、零向量调用；
- 构建按 materializing、indexing、validating、published 状态推进；
- 任一步骤失败时恢复构建前的图、索引与清单，并记录 failed 和错误原因；
- 保留原有 `/materialize` 与 `/index` 接口，新增构建接口不破坏旧调用方。

## 4. 新增 API

```text
POST /api/v1/networks/{network_id}/builds
GET  /api/v1/builds/{build_id}
```

第一个接口立即执行一次本地构建并返回完整 BuildJob；第二个接口可查询该次构建的最终状态和变更统计。当前是同步 MVP，后续可把同一 BuildJob 契约接到任务队列而不改变响应模型。

## 5. 数据一致性与失败保护

构建开始前保存当前已发布快照。只有图更新、索引更新和最终数量校验都成功，任务才标记为 published。若索引服务中断，图中已经执行的局部变化会被恢复，检索仍然看到上一次成功版本。

这是一种适合本地 MVP 的补偿式切换。它解决了“更新一半就可见”的问题，但不是跨数据库的分布式事务。

## 6. 测试结果

```text
全量测试：39 passed
Ruff：通过
Mypy strict：56 个源文件通过
```

集成测试实际覆盖：首次全量构建、修改一条并新增一条、无变化重复构建、BuildJob 查询，以及模拟索引故障后的图数据回滚。

## 7. 当前限制

- CSV 文件仍会被完整扫描一次来计算期望状态；本阶段优化的是图写入和 Embedding 成本，而不是超大文件的分片读取；
- 当前同步执行，服务重启后不会自动续跑处于中间状态的任务；
- 本地 SQLite 中采用快照补偿，数据量很大时应改为 staging 表、版本指针原子切换和后台清理；
- 数据源 Schema 变化尚未自动生成可审核的建模提案，该能力由 S7 承接。

## 8. 给 S7 的要求

AI 发现新字段、新关系或新动作时只能创建草稿提案，不能直接修改已发布 BKN。人工审核并发布后，再调用 S6 构建接口应用新版本；这样 AI 的便利性不会绕过 S5 的安全门禁，也不会绕过 S6 的一致性保护。
