# MiniBKN S1 通用核心产品开发报告

> 完成日期：2026-08-16\
> 前置报告：[S0 基线与领域契约产品开发报告](MINIBKN_S0_BASELINE_CONTRACTS_DEVELOPMENT_REPORT.md)\
> 对应计划：[分步开发计划](../plans/MINIBKN_STEPWISE_DEVELOPMENT_PLAN.md)\
> 状态：已完成

## 1. 与 S0 的衔接

S0 要求 S1 必须复用统一 `EvidenceItem`，不能另造回答上下文格式。本阶段严格按这个接口实施：检索命中的 Schema、实例、关系和动作都转换为 `EvidenceItem`，回答器只读取这些证据，`AskResult` 也把同一批证据返回给调用方。

S0 定义的 BKN 生命周期也已进入当前网络模型。为保持原 API 语义，现有目录导入默认代表 `published`；草稿审核工作流留到 S7。

## 2. 这一阶段解决了什么

旧回答器虽然能正确展示供应链案例，但在代码中明确写了库存字段、安全库存字段、供应商对象和供应链问题关键词。换成 CRM 后，这段逻辑没有意义。

现在回答器不再认识任何行业名词。它只读取检索到的相关对象、对象间 BKN 关系和数据来源，再按统一格式输出。因此供应链和 CRM 使用同一个类、同一个 API 和同一种证据格式。

## 3. 已完成的产品能力

### 3.1 通用证据回答

`POST /api/v1/networks/{network_id}/ask` 保留原来的 `question`、`answer`、`context` 和 `citations`，新增 `evidence` 字段。这是向后兼容的新增字段。

每条证据说明它是什么、对应哪个实体、内容、来源和检索分数。关系也成为正式证据，而不是只存在于内部子图。

### 3.2 回答不再偷偷扫描全库

旧逻辑会加载全部对象，再用供应链公式筛选。新逻辑只使用本次召回实例及其一跳子图。这样回答和展示的证据一致，也为 Faithfulness 评测建立了正确边界。

### 3.3 CRM 完整链路

```text
客户/订单 CSV
→ BKN 导入
→ 数据发现
→ 7 个对象、4 条关系
→ 混合索引
→ 提问“星河科技有哪些订单？”
→ 返回客户、ORD-001、ORD-002、placed_by 关系和数据行引用
```

### 3.4 常见业务类型

- `decimal`：规范化为字符串，避免金额浮点误差；
- `date`：规范化 ISO 日期；
- `datetime`：规范化 ISO 时间和时区；
- `json`：解析为字典或数组。

CSV 发现可以识别 date、datetime 和 JSON；SQLite 类型映射也补充了对应类型。

### 3.5 网络生命周期

`KnowledgeNetwork` 和网络列表响应新增 `lifecycle_status`。当前导入版本为 `published`，为后续草稿、审核、批准流程预留兼容字段。

## 4. 关键代码变化

- 新增 `domain/base.py`，让各领域合同共享冻结配置；
- 新增 `application/answer_generator.py`，实现领域无关的确定性回答；
- 修改 `application/retrieval_service.py`，删除供应链专属判断并组装统一证据；
- 修改 `application/graph_service.py` 和数据源适配器，扩展业务数据类型；
- 修改 API Schema，增加生命周期状态；
- 新增 CRM 端到端测试和类型规范化测试。

## 6. 用户现在能看到什么变化

- 同一个系统可以导入供应链或 CRM BKN；
- 问答响应中可以直接查看机器可读的证据；
- 回答会展示相关对象的实际字段和关系，不再固定输出库存话术；
- 网络响应会显示当前模型是否为已发布版本。

## 7. 当前限制

- 目前仍是“检索后摘要”，不能严格执行“金额最高的三个客户”或“库存低于安全库存”这类聚合、排序和字段比较；返回的相关对象中可能包含不满足条件的对象，这属于 S4 QueryPlan 的解决范围；
- 回答器是确定性兜底版，还没有接 LLM 做自然语言整合；
- 当前上下文固定为一跳和固定数量，证据预算合同尚未接入执行；
- CRM 是回归样例，不是最终 200 题评测集；
- 生命周期目前只有发布状态进入真实网络，草稿提案尚未持久化。

## 8. 给 S2 的接口与要求

下一步做主外键发现时，输出必须形成可审核的 `SchemaProposal`，并附带统计证据与置信度。用户确认前，不得把推断关系直接写成已发布 BKN。S2 新增字段类型必须继续输出 JSON 可持久化值，不能破坏本阶段的 CRM 回归链路。
