MiniBKN 现在不只是“能读懂图谱定义”，而是已经能把真实 CSV/SQLite 数据变成对象和关系，
再通过 BM25 + 向量 + RRF 找资料、拼出三层上下文，并回答带来源的问题。

- MCP 尚未接入。

这个口径非常重要：面试官追问时，每一句都应该能现场运行或拿测试结果证明。

## 这次具体做了什么

### 1. 让系统真正读到业务数据

现在可以注册一个 CSV 文件/目录或 SQLite 数据库。系统会自动发现里面有哪些文件或表、每个
字段叫什么、是什么类型、是否可能是主键，以及一共有多少行。

供应链示例中，系统发现了：

- `materials.csv`：3 条物料数据。
- `suppliers.csv`：2 条供应商数据。

### 2. 把二维表变成业务知识图

系统读取 BKN 中的映射规则，把 5 行数据变成 5 个业务对象，再根据 `supplier_id` 生成 3 条
“物料由供应商供应”的关系。

例如从温度传感器 `MAT-001` 出发查询一层子图，会得到：

```text
Temperature Sensor (MAT-001)
  -- supplied_by -->
Precision Components (SUP-001)
```

这已经解决了普通向量 RAG 常见的一个问题：信息不再只是互相独立的文本片段，系统知道两个
业务实体之间为什么有关联。

### 3. 实现可解释的混合检索

每份 Schema、业务实例和行动都会生成检索文档。查询时系统同时走两条路：

- BM25：擅长精确关键词、编号、字段名。
- 向量相似度：当前使用无需下载模型的确定性离线向量基线。

两路结果用 RRF 合并。API 会直接返回 `bm25_rank`、`vector_rank` 和最终 `score`，因此可以
清楚解释“为什么这个结果排在前面”。

### 4. 拼出三层上下文，而不是一次塞一堆文本

`/ask` 的上下文被分成：

1. Schema：问题涉及什么对象、字段和关系。
2. 实例与子图：具体是哪条物料、供应商，以及它们怎么相连。
3. 行动：找到相关的补货预警行动，供下一阶段执行。

每条证据都带引用：Schema 使用 `bkn://...`，数据使用
`resource://materials_csv#row=2` 这种定位方式。回答错了时，可以反查它用了哪份定义和哪一行数据。

## 实际演示结果

问题：

> 哪些物料库存低于安全库存，它们由谁供应？

系统能找出：

- Temperature Sensor（MAT-001）：当前库存 8，安全库存 30。
- Relay Module（MAT-003）：当前库存 4，安全库存 25。
- 两者供应商都是 Precision Components。

这条链路从数据源发现、图实例化、索引、检索、关系补全一直走到最终回答，不需要外部数据库、
向量库或 LLM Key。

## 下一阶段会做什么

阶段 C 会把当前第三层的“行动建议”变成真正可控的业务执行：

```text
检索到库存不足
  -> 选择补货预警行动
  -> 自动绑定并校验参数
  -> 检查风险策略
  -> 需要时等待人工确认
  -> 调用白名单工具
  -> 用 trace_id 记录全过程
```

完成这一步后，项目才真正形成“数据 → 图谱 → 检索 → 回答 → 行动”的完整业务闭环。之后再
升级真实多语言语义模型、AI Schema、MCP 和 Ragas 评测，简历中的每项能力就能逐步变成有
证据的项目成果。
