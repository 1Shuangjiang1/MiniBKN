## 一、这份方案是干什么的？

这是一份把MiniBKN从"供应链Demo"升级成"通用企业级知识引擎"的完整执行蓝图，是秋招前开发的总纲领。

简单说，当前0.4.0版本只能演示供应链库存一个场景，换客户、订单场景就跑不通。这份方案要解决这个问题，把系统做成：
- 支持任意结构化业务场景（CRM、ERP、HR等），不用改代码
- AI全程辅助建模，但所有核心环节有人工审核，保证安全准确
- 有QueryPlan查询规划，支持多跳关联、过滤、聚合等复杂查询
- 通用风险规则引擎，支持在BKN里配置任意风控规则
- 有真实的评测数据，简历上的每个数字都能复现
- 可选接入LightRAG支持非结构化文档（PDF/Word）
- 有简单UI方便演示

---

## 二、核心原则（必须遵守）

方案反复强调一条红线，也是面试最重要的亮点：

> **AI只负责提建议、做解释、生成草稿；确定性程序负责校验、发布、执行、审计。**

AI绝对不能做的7件事（原方案第5.2节）：
1. 不能直接执行SQL、Python、Shell等任意代码
2. 不能绕过工具注册表调用外部系统
3. 不能自己宣布风险通过直接执行动作
4. 不能未经确认就发布主外键、动作、风险规则
5. 不能把用户提示词里的话当权限证明（防提示词注入）
6. 不能修改删除审计日志
7. 不能基于文档证据触发业务动作

这个设计非常重要，是MiniBKN和普通"全链路LLM"RAG的本质区别，面试一定要讲清楚。

## 四、目标架构（一张图看懂）

```
用户/UI → FastAPI接口
    ↓
建模流程：
  数据源 → 数据剖析 → AI提案 → 草稿工作区 → 人工确认 → 校验编译 → 版本发布
    ↓
增量构建 → 对象关系图 + BM25/向量索引
    ↓
查询流程：
  用户问题 → 查询路由器
    ├→ 结构化查询 → QueryPlan生成校验 → 确定性执行器 → 查图/索引
    ├→ 文档查询 → LightRAG外置服务（可选）
    └→ 混合查询 → 两边并行召回
    ↓
统一证据层 → LLM生成带引用回答 → 返回用户
    ↓
动作流程：
  用户发起动作 → 风险规则引擎
    ├→ 允许 → 工具注册表执行
    ├→ 需确认 → 人工审批 → 执行
    └→ 拒绝 → 记录审计
    ↓
  全程审计日志
```

### 关键边界一定要记住：
- MiniBKN是结构化事实的权威来源，总控路由、证据、回答、动作安全
- LightRAG只负责非结构化文档召回，不碰动作执行
- UI是独立前端，只调用公开API，不把页面逻辑塞进核心
- BKN只存声明式规则，工具必须提前注册，不能在BKN里写任意脚本执行

## 五、P0核心内容详解（秋招前必须做完）

按原方案第14.1节，秋招前优先级是：
`S0 → S1 → S2 → S3 → S4 → S5最小版 → S10结构化评测`

### S0：基线与契约（2-3天）
- 冻结0.4.0现有行为和测试结果
- 定义核心新领域模型：
  - `EvidenceItem`：统一证据格式，不管来自结构化还是文档
  - `QueryPlan`：结构化查询计划
  - `SchemaProposal`：AI提案
  - `BknVersion`：BKN版本管理
  - `BuildJob`：构建任务
- 准备最小CRM数据样例
- 先写"移除供应链硬编码"的失败测试

### S1：通用核心（4-6天）
- **删除所有供应链硬编码**：再也不写死`current_stock < safety_stock`这种逻辑
- 支持通用数据类型：date、datetime、decimal、enum、json、可空、组合键
- 基于统一证据层做回答生成
- BKN版本生命周期：draft → reviewed → approved → published
- 要求：CRM和供应链两套数据走同一套引擎，不用改代码

### S2：主外键增强（6-8天）
分层发现流程：
1. **数据库元数据优先**：SQLite/MySQL直接读声明的主键外键，可信度100%
2. **列级数据剖析**：算空值率、唯一率、基数、类型、长度、格式、熵、样例值
3. **候选主键**：先单列，再找最多3列的组合主键（避免组合爆炸）
4. **候选外键**：算两个字段的包含率、孤儿率、类型兼容、名称相似、值域重合
5. **评分排序**：按公式打分（原方案6.2节），≥0.9高置信，0.7-0.9普通候选，<0.7不推荐
6. **LLM只做语义重排**：对已有候选解释和排序，不凭空编造关系
7. **人工确认**：展示证据、反例、影响范围，用户可以接受/修改/拒绝/锁定
8. **持续验证**：新数据进来监控唯一性、孤儿率、Schema漂移

### S3：真实Embedding（3-5天）
- 默认用硅基流动的`BAAI/bge-m3`：多语言、1024维、免费额度足够开发
- 支持批量请求、超时、重试、限流、熔断、失败降级到BM25
- 向量缓存键：模型+维度+内容哈希
- 索引版本化：换模型自动建新索引，不混写
- Token哈希和SentenceTransformer本地模型保留作为降级选项

### S4：QueryPlan（7-10天）
LLM不直接生成SQL，生成受约束的JSON计划：
```json
{
  "intent": "aggregate",
  "object_types": ["customer", "order"],
  "filters": [{"field": "order.created_at", "op": ">=", "value": "2026-01-01"}],
  "traversals": [{"relation": "customer_placed_order", "direction": "out"}],
  "aggregates": [{"fn": "sum", "field": "order.amount", "alias": "total"}],
  "group_by": ["customer.id"],
  "limit": 10
}
```
执行流程：
1. 拿已发布BKN和用户权限
2. LLM生成计划 → Pydantic校验格式
3. 按BKN白名单检查对象、字段、关系、操作符是否合法
4. 检查跳数、扫描范围、上下文预算，防止查太多
5. 确定性执行器做过滤、图遍历、聚合
6. 原始事实+关系路径+计算结果全部封装成证据
7. LLM只基于证据生成最终回答

失败策略：计划不合法只允许修复一次，再失败直接降级到普通检索，绝不执行LLM生成的任意文本。

### S5：风险规则最小版（不用全做，做最小可用）
- 安全AST表达式引擎，不用eval，只允许比较、逻辑、算术、集合包含
- 规则冲突默认deny > confirm > allow
- 计算异常fail closed（拒绝执行，不冒险）
- 动作必须用户明确发起，AI推荐不能自动执行

### S10：结构化评测（7-10天）
- CRM数据集：500客户、2000-3000订单、6000-10000明细、100+产品、15-30销售
- 冻结评测集：200道结构化题 + 30道动作安全题
- 5个基线对比：BM25、纯向量、BM25+向量RRF、加Reranker、QueryPlan+三层上下文
- 完整指标：Hit@K、MRR、nDCG、Context Precision/Recall、Faithfulness、引用准确率、参数正确率、风控准确率、Token消耗、延迟
- 所有数字必须可复现，不达到预期也没关系，真实最重要

## 八、面试怎么讲这份架构设计

面试官问"你这个项目和普通RAG有什么区别？"，可以这么答：

1. **确定性边界设计**：我们严格划分了AI和确定性代码的边界，数据建模、关系物化、风控判定、工具执行、审计这五条红线100%是确定性代码，AI只做理解和生成，从架构上避免了幻觉和越权问题
2. **三层上下文+QueryPlan**：我们不是盲目把TopK文档塞给LLM，而是先生成受Schema约束的结构化查询计划，确定性地做过滤、图遍历、聚合，再组装Schema-实例-动作三层上下文，既提升了准确率，又降低了Token消耗
3. **声明式业务建模**：所有对象、关系、动作、风控都用BKN声明式配置，不用改代码就能支持新业务场景，有完整的草稿-审核-发布版本流程
4. **混合检索架构**：结构化数据走我们自己的确定性链路保证准确，非结构化文档可以通过LightRAG并行接入，统一证据层做融合，动作执行始终在MiniBKN风控链路内
5. **完整评测体系**：我们不是凭感觉说效果好，而是在冻结CRM测试集上做了多组基线对比，用Ragas的Context Precision/Faithfulness等指标量化，所有数字可复现
