# MiniBKN 后续优化路线图

> 文档版本：1.0
> 编写日期：2026-08-15
> 当前版本：0.4.0
> 优化方向：普适性、AI智能性、架构合理性、稳定性、容错性

---

## 一、现状总结与优化目标

### 1.1 当前已实现能力（0.4.0基线）

| 模块 | 现状 |
|------|------|
| 数据接入 | CSV/SQLite导入，自动发现表结构 |
| 建模 | BKN文件解析、纯规则自动Schema生成（主键/外键）、AI补描述（可选） |
| 存储 | SQLite持久化，8张核心表 |
| 检索 | BM25+Token哈希向量RRF混合检索，三层上下文分组，1跳BFS子图扩展 |
| 问答 | 供应链场景硬编码抽取式回答 |
| 动作执行 | 参数绑定、硬编码金额阈值风控、白名单工具、审计Trace |
| 接口 | FastAPI REST + Swagger + MCP stdio Server |
| 质量 | 13个Pytest通过，200条供应链模板题检索评测 |

### 1.2 当前核心问题

| 问题分类 | 具体问题 | 影响 |
|----------|----------|------|
| **普适性** | 问答硬编码供应链库存逻辑，换场景跑不通 | 只能演示Demo，不能称为通用引擎 |
| **普适性** | 主键外键识别规则简单，字段名不匹配时无法自动发现关系 | 新场景需要大量手动配置BKN |
| **智能性** | 默认向量是Token哈希，无真实语义理解 | 检索效果上限低，语义匹配差 |
| **智能性** | AI只在Schema描述补全时使用，问答、查询规划都没用LLM | 回答生硬，无法理解复杂问题 |
| **架构** | bkn_documents表只写不读，knowledge_networks大JSON读写性能差 | 遗留冗余，大网络下性能问题 |
| **架构** | 风控规则硬编码，只能算补货金额，不支持自定义表达式 | 新的风控规则需要改代码 |
| **稳定性** | 无缓存，每次检索都读全表 | 数据量大后性能下降 |
| **容错性** | 错误处理简单，没有降级策略，没有重试机制 | 异常场景体验差 |
| **评测** | 200题是模板生成的，没有真实CRM场景，没测Faithfulness等指标 | 简历数字没有真实数据支撑 |

### 1.3 优化原则

1. **秋招优先**：P0优先级保证秋招前完成，拿到真实评测数据，简历有东西可讲
2. **确定性边界**：数据、关系、风控、执行仍然保持确定性，AI只做理解和生成
3. **可演进**：所有优化保持架构兼容，可以逐步迭代，不用大改
4. **真实可测**：所有性能/效果数字必须有真实测试结果，不造假
5. **面试友好**：每个优化点都能讲出设计思路、权衡、效果，适合面试深挖

**目标**：从"供应链Demo"变成"通用轻量级知识引擎"，拿到真实评测数据，简历数字全部可复现。

### P0-1：通用问答层替换硬编码逻辑

**问题**：当前问答写死了`current_stock < safety_stock`判断，只能回答库存问题。

**优化方案**：实现基于三层上下文的通用抽取式回答模板+可选LLM生成双模式。

#### 具体实现：

1. **通用抽取式回答（规则版，无需LLM）**
   - 从问题中提取关键词匹配Schema字段名/显示名/描述
   - 识别简单比较操作：大于/小于/等于/包含
   - 自动从实例中筛选符合条件的对象
   - 自动把子图中的关联对象信息拼接进回答
   - 证据不足时拒答，返回找到的相关对象列表
   - 保留所有来源引用

2. **LLM生成式回答（可选，配API Key开启）**
   - 设计严格的System Prompt：
     - 只能使用提供的上下文回答，禁止外部知识
     - 每个事实必须附citation引用
     - 证据不足明确说"我没有足够信息回答"，禁止编造
     - 支持数值计算（统计、求和、比较）
   - 把Schema、实例、子图、动作序列化成清晰的结构化提示词
   - 解析LLM输出，验证引用是否真实存在
   - 增加事实校验环节：LLM输出的每个事实，检查是否能在上下文中找到依据

**代码改动点**：
- 重写`retrieval_service.py`的`_extractive_answer()`方法，拆成通用规则回答
- 新增`adapters/llm/openai_compatible.py`（已存在，补完）
- 新增LLM回答服务类，做提示词组装、输出解析、引用校验
- config里加回答模式配置：`extractive`/`llm`

**验收标准**：
- 供应链场景原有问答能力不下降
- 新增CRM场景（客户、订单、产品）不需要改代码，只需要导入数据和BKN就能回答80%常见问题
- 回答每个事实都有引用来源

**面试可以讲**："我们设计了双模式回答层：规则抽取模式保证零依赖、可预测、高性能；LLM模式在保证引用校验和事实边界的前提下提供自然语言回答，两种模式共享三层上下文和证据模型，可以按需切换。"

### P0-2：主键外键识别增强

**问题**：当前主键只识别id/sku/_id结尾，外键只识别同名主键，字段名不匹配就识别不了。

**优化方案**：多维度启发式识别+评分排序+AI推荐+用户确认。

#### 具体实现：

1. **扩展命名规则**
   - 主键：增加`*_no`、`*_code`、`*_num`、`*_id`、`uuid`、`guid`、`编号`、`编码`、`号`
   - 排除明显非主键字段：email、phone、mobile、name、date、time、amount、price、cost、desc、address、status
   - 前缀后缀权重：id结尾权重100，code结尾权重80，no结尾权重70

2. **数据特征评分**
   - 非空且唯一：+50分
   - 值是自增整数（近似连续）：+30分
   - 值有固定格式正则（如`^[A-Z]+-\d+$`）：+20分
   - 平均值长度在合理范围（5-20字符）：+10分
   - 重复值超过1%：直接排除
   - 空值率>0：直接排除

3. **外键识别增强**
   - 同名xxx_id匹配：+100分（保持原有规则）
   - 字段名相似匹配：如vdr_code和vendor_id，编辑距离<3：+40分
   - 值集合包含关系：源表字段的值集合是目标表主键值集合的子集：+60分（非常强的信号）
   - 数据类型匹配：+10分
   - AI推荐（可选）：当置信度在40-80分之间时，调用LLM根据字段名和样例值判断是否是外键

4. **用户确认环节**
   - 自动识别后展示识别结果，标注置信度
   - 用户可以手动修改主键、增删外键关系
   - 用户确认后保存到Schema，不用每次重新识别

**代码改动点**：
- 重写`adapters/datasource/local.py`的`_looks_like_primary_key()`，改成评分制
- 新增`schema_generation_service.py`里的外键评分逻辑
- 可选：新增AI外键推荐方法
- API增加Schema确认/调整接口

**验收标准**：
- 标准命名的主键外键识别准确率100%
- 字段名相似但不相同的外键（如vendor_code对应supplier_id）识别准确率≥80%
- 提供人工调整入口，保证最终Schema100%正确

### P0-3：真实语义向量替换Token哈希默认值

**问题**：默认Token哈希是伪向量，无语义理解能力，检索效果差。

**优化方案**：Sentence Transformers作为默认向量，Token哈希作为零依赖兜底。

#### 具体实现：

1. **依赖调整**
   - 把sentence-transformers从extra依赖改成默认依赖
   - 默认模型用`paraphrase-multilingual-MiniLM-L12-v2`：支持中文，体积小（~100MB），速度快，效果好
   - 第一次运行自动下载模型到本地缓存，不需要用户手动操作
   - 保留Token哈希作为离线/无网络环境兜底，通过配置切换

2. **向量检索优化**
   - 向量归一化，用余弦相似度计算
   - 支持批量编码，建索引速度更快
   - 缓存常用查询向量（可选）

3. **混合检索权重调优**
   - 重新跑200题评测，调优RRF的k值和BM25/向量的权重
   - 中文分词优化：当前正则对中文是单字分词，可以加jieba分词提升BM25效果（可选）

**代码改动点**：
- 修改`config.py`默认值：`embedding_provider = "sentence_transformers"`
- 优化`hybrid.py`的中文分词（可选，加jieba）
- 补完`semantic.py`的错误处理，模型下载失败自动降级到Token哈希

**验收标准**：
- 默认开箱即用真实语义向量，不需要额外配置
- Hit@1、MRR等检索指标比Token哈希有明显提升
- 模型下载失败自动降级，不会崩溃

**面试可以讲**："我们对嵌入层做了可插拔设计，默认使用开源的多语言Sentence Transformer模型保证语义检索效果，同时保留Token哈希作为零依赖兜底方案，兼顾效果和开箱即用体验。"

### P0-4：CRM场景建设+完整Ragas评测

**问题**：当前200题是模板生成的，没有真实业务场景，没有Faithfulness等指标。

**优化方案**：构建CRM真实测试集，跑完整Ragas评测，拿到真实数字写简历。

#### 具体实现：

1. **CRM测试集建设**
   - 设计4个核心对象：客户(customer)、订单(order)、产品(product)、订单明细(order_item)
   - 生成模拟真实数据：~50个客户，~200个订单，~30个产品，~500条订单明细
   - 设计50-100道真实业务问题，覆盖：
     - 单对象查询（"张三的电话号码是多少"）
     - 1跳关联（"张三下了哪些订单"）
     - 2跳关联（"买了产品A的客户都有谁"）
     - 条件过滤（"金额大于1000的订单有哪些"）
     - 聚合统计（"本月订单总金额是多少"、"每个客户的订单数"）
     - 动作相关（"哪些订单需要审批"）
   - 每道题人工写标准答案和应该命中的引用

2. **跑完整Ragas指标**
   - Context Precision：检索回来的上下文有多少是相关的
   - Context Recall：应该检索到的上下文有多少真的检索回来了
   - Faithfulness：回答里有多少是能被上下文支持的（幻觉率）
   - Answer Relevance：回答和问题的相关度
   - 对比三个基线：
     1. 纯向量检索（普通RAG基线）
     2. 纯BM25检索
     3. MiniBKN三层混合检索+子图扩展
   - 统计上下文Token消耗量对比

3. **简历数字替换**
   - 所有数字用真实跑出来的结果，哪怕没有达到之前的目标值也没关系，真实最重要
   - 如果提升20%就写20%，提升15%就写15%，重点讲设计思路和为什么能提升

**代码改动点**：
- 新增`examples/crm/`目录，放CRM的CSV数据、BKN文件
- 完善`evaluation/benchmark.py`，支持Ragas指标计算
- 生成评测报告，保存原始结果

**验收标准**：
- CRM场景不需要改代码，直接导入就能回答问题
- 有完整的评测脚本，可以一键复现所有数字
- 对比数据清晰，MiniBKN相对基线的提升有数据支撑

**面试可以讲**："我们基于Ragas框架构建了CRM场景测试集，对比实验显示，相比纯向量RAG基线，我们的三层混合检索+子图扩展方案在Context Precision、Faithfulness等指标上有明确提升，同时上下文Token消耗降低，因为我们只返回相关的结构化数据而不是大量无关文档块。"

### P0-5：风险规则表达式引擎

**问题**：当前风控硬编码补货金额计算，加新规则必须改代码。

**优化方案**：实现安全的简单表达式引擎，支持在BKN里写风控条件。

#### 具体实现：

1. **表达式语法设计（简单安全）**
   - 支持：算术运算(+,-,*,/)、比较运算(>,<,>=,<=,==,!=)、逻辑运算(&&,||,!)
   - 支持：属性访问（`properties.current_stock`、`properties.unit_cost`）
   - 支持：内置函数（max、min、sum）
   - 禁止：函数调用、导入、循环、赋值、任意代码执行

2. **安全执行**
   - 用Python AST解析表达式，白名单只允许允许的节点类型
   - 执行时只注入instance.properties作为上下文，不提供任何其他内置函数
   - 表达式执行超时控制（最多100ms），防止死循环

3. **BKN配置方式**
   ```yaml
   # risk_type BKN frontmatter
   condition:
     expression: "(safety_stock - current_stock) * unit_cost >= threshold"
     threshold: 500
   ```

4. **内置常用规则模板**
   - 金额阈值（已有）
   - 数量阈值
   - 字段值等于/不等于
   - 组合条件（A且B）

**代码改动点**：
- 新增`domain/rule_engine.py`，实现安全表达式解析和执行
- 修改`action_service.py`的`_risk_decision()`，支持通用表达式
- 更新parser，支持从BKN读取expression
- 增加规则引擎单元测试，覆盖各种边界情况

**验收标准**：
- 补货金额规则不用改代码，通过BKN表达式配置
- 可以配置新的风控规则（如订单金额>10000需要审批），不需要改代码
- 恶意表达式（如`__import__('os').system('rm -rf /')`）无法执行
- 表达式执行错误有清晰的错误提示

### P1-1：Query理解与查询规划

**问题**：当前直接把用户问题拿去做检索，没有理解查询意图，复杂问题效果差。

**优化方案**：LLM做查询理解，生成结构化查询计划，指导检索和回答。

#### 具体实现：

1. **查询意图识别**
   - 识别问题类型：事实查询/条件过滤/聚合统计/关系查询/动作请求
   - 识别需要的对象类型
   - 识别过滤条件（字段、操作符、值）
   - 识别需要的关联深度（1跳/2跳）

2. **结构化查询计划**
   ```json
   {
     "query_type": "filter_with_relation",
     "target_object": "material",
     "filters": [{"field": "current_stock", "op": "lt", "value_field": "safety_stock"}],
     "expand_relations": ["supplied_by"],
     "expand_depth": 1,
     "need_actions": true
   }
   ```

3. **基于查询计划做检索**
   - 不是全局盲目搜Top20，而是优先检索目标对象类型
   - 按查询计划决定子图扩展深度
   - 聚合类问题直接在结构化数据上做计算，不用LLM瞎算

**价值**：复杂多跳问题、聚合问题准确率大幅提升，Token消耗更可控。

---

### P1-2：增量更新与索引优化

**问题**：当前改Schema/数据都是全量重建，bkn_documents表没用上。

**优化方案**：利用bkn_documents表做细粒度更新，增量重建索引。

#### 具体实现：

1. **bkn_documents表启用**
   - 单个BKN文档更新时，只更新对应行，不用重写整个knowledge_networks大JSON
   - 提供单个文档CRUD接口

2. **增量物化**
   - 支持单条/批量新增/更新/删除对象实例
   - 数据变化时只重新计算受影响的关系边（源对象或目标对象变化了才重算）
   - 增量更新search_documents，不用全表删了重建

3. **检索性能优化**
   - BM25索引预计算并缓存（当前每次search都重新算BM25分数，数据量大了慢）
   - 向量可以存成numpy数组，加速相似度计算
   - 热门查询缓存结果

---

### P1-3：AI辅助建模增强

**问题**：当前AI只补描述，建模还是要大量人工。

**优化方案**：全流程AI辅助建模，用户确认即可。

#### 具体实现：

1. **AI主键外键推荐**：置信度低的候选自动调用LLM判断
2. **AI字段语义识别**：自动识别字段是邮箱/电话/金额/日期/地址等，生成描述
3. **AI推荐动作和风控**：根据对象和字段自动推荐常用动作（如创建补货预警、审批）和风控规则
4. **自然语言建模**：用户用自然语言说"我要加一个客户和订单的关系，一个客户有多个订单"，AI生成RelationType BKN
5. **AI BKN文件生成**：上传CSV后，AI一键生成完整的BKN文件，用户下载下来可以手动调整

---

### P1-4：简单前端UI

**问题**：当前只有API和MCP，演示不够直观。

**优化方案**：用Gradio/Streamlit做一个简单的演示UI，不用复杂前端。

#### 功能：
- 数据源导入和Schema展示
- 问答对话界面，展示引用来源和三层上下文
- 知识图谱可视化（用pyvis简单展示节点和边）
- 动作执行和审批界面
- 评测结果展示

**价值**：面试演示更直观，不用对着Swagger讲。

---

### P1-5：LightRAG非结构化文档并行接入

**问题**：当前只支持结构化数据，不支持PDF/Word等文档。

**优化方案**：LightRAG作为独立可选服务接入，并行检索，结果融合。

#### 具体实现（参考已有规划文档）：
- LightRAG独立部署，不嵌入核心代码，通过REST API调用
- 统一证据模型和引用格式
- 检索时同时查MiniBKN结构化数据和LightRAG非结构化文档
- 结果融合后一起返回给LLM
- 动作执行仍然走MiniBKN的风控链路

**面试可以讲**："我们采用混合检索架构，结构化业务数据走MiniBKN确定性链路保证准确，非结构化文档通过LightRAG并行接入，两者共享统一的证据和引用模型，既支持结构化业务查询和动作执行，又支持文档知识问答。"

## 四、P2优先级（架构增强和生产化，长期，约1个月+）

**目标**：架构更合理、稳定、容错，适合生产环境使用，增加深度面试亮点。

---

### P2-1：架构分层和端口适配器完善

**问题**：当前ports/adapters分层已经有雏形，但可以更清晰。

**优化方案**：
- 完善端口接口定义，所有领域逻辑依赖抽象不依赖具体实现
- 增加PostgreSQL适配器（替换SQLite）
- 增加外部工具HTTP调用适配器（当前只有本地工具）
- 增加更多LLM适配器（豆包、通义千问、DeepSeek等）
- 依赖注入容器，方便测试和扩展

---

### P2-2：稳定性和容错性增强

**优化方案**：
1. **错误处理和降级**
   - LLM调用失败自动降级到规则回答
   - 模型下载失败自动降级到Token哈希
   - 向量检索失败自动降级到纯BM25
   - 友好的错误提示，不暴露堆栈信息

2. **重试和熔断**
   - 外部LLM/工具调用增加重试机制（指数退避）
   - 外部服务不可用时熔断器打开，快速失败

3. **参数校验和输入防护**
   - 所有API参数严格校验
   - 查询长度限制，防止超长查询拖垮系统
   - 提示词注入防护：用户问题做简单清洗，防止绕过系统提示词

4. **日志和监控**
   - 结构化JSON日志
   - 关键指标监控：检索耗时、LLM调用耗时、命中率、错误率
   - 每个请求完整trace链路，可以排查问题

---

### P2-3：多级缓存机制

**优化方案**：
- L1缓存：热门查询的检索结果缓存（内存，TTL 5分钟）
- L2缓存：BM25索引、向量索引缓存（启动时加载，增量更新）
- L3缓存：LLM回答缓存（相同问题直接返回，不用重复调用LLM）
- 缓存失效机制：数据更新时自动失效相关缓存

---

### P2-4：权限控制（RBAC简化版）

**优化方案**：
- API Key认证（已有基础）
- 简单的角色划分：管理员（可改Schema/执行动作）、普通用户（只能查询）、审计员（只能看日志）
- 按知识网络做权限隔离
- 动作审批人配置，不同金额等级找不同人审批

---

### P2-5：多跳子图可配置

**优化方案**：
- ask接口支持配置子图扩展深度（1跳/2跳/3跳）
- 根据查询复杂度自动决定扩展深度
- 循环引用检测，防止无限扩展
- 扩展节点数上限，防止返回太多数据撑爆上下文

## 七、风险和注意事项

1. **不要贪多**：先保证P0全部完成，有真实评测数据，再做P1/P2，P0没做完不要碰P2
2. **真实性红线**：所有简历上的数字必须是真实跑出来的，哪怕提升不大也没关系，真实比好看重要
3. **测试覆盖**：每个优化点加对应的单元测试，保证主链路不挂
4. **保持可演示**：每个阶段都要有一个可以跑通的端到端Demo，随时可以演示
5. **不要过早优化**：数据量没到万级/十万级，不用太担心性能问题，先保证正确和通用，再优化性能
