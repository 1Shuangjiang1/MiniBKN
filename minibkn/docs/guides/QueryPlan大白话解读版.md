## 先纠正一个常见误解：QueryPlan不是"关键词扩展"

你可能以为：用户问题说的不明确，系统就把问题改一改，扩展点同义词，再去搜索。这个想法没错，但这叫**查询改写**，不是QueryPlan的主要活。

### 那QueryPlan到底是什么？

QueryPlan就是一张**"查数据工单"**：
- 用户说一句人话
- AI把这句话翻译成系统能看懂的、一步步的"施工单"
- 工单上写清楚：查什么表、筛什么条件、跳什么关系、怎么算、返回多少
- 代码严格检查工单合不合法，不合法直接打回
- 合法就按工单一步步硬算，不用AI猜

**生活类比**：
你去政务大厅办事，跟窗口说"我要办社保"，窗口人员不会直接给你办，而是先给你一张办事单，勾清楚：办什么业务、要什么材料、走什么流程、去哪几个窗口盖章、最后拿什么结果。这张办事单就是QueryPlan，你拿着按步骤走就行，不会瞎办。

### 举个例子你就懂了

用户问："已支付并且金额大于等于一万块的订单，总金额加起来是多少？"

如果是**关键词检索**，就是提取"订单、支付、一万、总金额"这些词，去文档库里找相关的片段，丢给AI让AI自己算。
如果是**QueryPlan**，就是生成一张明确的工单：
```
1. 查【订单】表
2. 筛选条件：
   - 状态 = 已支付
   - 金额 ≥ 10000
3. 对筛选出来的订单，把【金额】字段加起来
4. 返回总和，以及参与计算的所有订单证据
```
代码按这个工单一步步算，算完把结果返回给AI，AI只负责把结果写成自然语言。

**核心区别**：检索是"找相关材料给AI自己看"，QueryPlan是"写好明确步骤让代码硬算"，后者更准、更快、更省钱，还不会算错数。

## 先搞清楚三个容易混的概念

| 概念 | 通俗比喻 | 解决什么问题 | 现在做完了吗 |
|------|----------|--------------|--------------|
| **查询改写** | 你说话说一半、说错字、用了简称，帮你把话说明白 | 错别字、同义词、简称、指代不清（"他那个订单"的"他"是谁） | ❌ 还没做 |
| **普通检索** | 按关键词/意思找相关材料 | "哪些内容和这个问题有关"，找参考资料 | ✅ 已经有了（BM25+向量+RRF混合） |
| **QueryPlan** | 开可执行的办事工单 | 明确查什么、怎么筛、跳什么关系、怎么算、返回多少 | ✅ 执行器100%做完了；AI自动生成正确工单还需要加强 |

现在系统两个接口：
- `/search`：走普通检索，找相关材料
- `/ask-planned`：走QueryPlan流程，开工单硬算

## 完整流程走一遍（从你问问题到拿到答案）

```
你问问题
   ↓
AI/规则规划器生成QueryPlan工单
   ↓
代码检查工单合不合法：
   ├─ 查的对象（表）在BKN里存在吗？
   ├─ 筛的字段存在吗？类型对吗？
   ├─ 要跳的关系存在吗？让跳几跳？
   ├─ 聚合函数是允许的吗？（count/sum/avg/max/min可以，其他不行）
   └─ 返回数量超了吗？Token预算超了吗？
   ↓
不合法 → 直接返回错误，让AI改一次，再错就降级到普通检索
   ↓
合法 → 确定性执行器按工单一步步干：
   1. 按条件筛选符合要求的对象
   2. 需要跳关系就沿关系找关联对象（比如找订单对应的客户）
   3. 需要聚合就硬算（count/sum/avg...）
   4. 限制返回结果数量，控制证据条数
   ↓
所有结果都带来源（来自哪张表哪一行）
   ↓
AI基于这些硬算出来的证据写自然语言回答
   ↓
返回答案+引用
```

如果问题里有要执行动作的意思（比如"给我创建补货单"）：
- 不会直接在查询里执行动作
- 只是校验一下这个动作合法不合法
- 动作单独走风控、审批、执行那条链路，和查询分开

## QueryPlan工单上能写什么？

我给你一个个讲，每个字段是什么意思，能干什么：

| 字段 | 是什么意思 | 举个例子 | 现在支持吗 |
|------|-----------|----------|------------|
| `intent` | 你要干什么类型的事 | 搜索、精确找、跳关系、算统计、执行动作 | ✅ 5种都支持 |
| `object_types` | 查什么东西 | 查客户？还是订单？还是物料？ | ✅ |
| `select` | 最后返回哪些字段 | 返回客户名字、电话、订单金额？还是全部？ | ✅ |
| `filters` | 筛选条件 | 状态=已支付、金额≥10000、创建时间≥2026-01-01 | ✅ 支持等于、大小比较、在集合里、模糊匹配、字段存在 |
| `traversals` | 沿关系跳 | 找到订单后，跳一跳找到下单的客户 | ✅ 最多跳5跳，足够用了 |
| `aggregates`/`group_by` | 统计计算 | 算总数、求和、平均、最大最小，按什么分组 | ✅ count/sum/avg/max/min都支持 |
| `order_by` | 排序 | 按金额从高到低排 | ⚠️ 聚合结果排序支持，普通明细排序还没做完 |
| `limit` | 返回多少条 | 最多返回10条还是100条 | ✅ 1-100条 |
| `evidence_budget` | 证据预算 | 最多给多少条证据，最多用多少Token，防止撑爆上下文 | ⚠️ 证据条数限制做了，Token预算还没完全落实 |
| `answer_mode` | 回答格式 | 返回纯文本、表格还是列表 | ⚠️ 字段有了，展示层还没区分 |
| `action_request` | 要执行动作吗 | 要不要创建补货单/退款 | ✅ 能校验合不合法，但不会直接执行，要单独走风控流程 |

**最重要的红线**：工单上写的所有对象、字段、关系、动作，必须是已经在发布的BKN（规章制度）里写了的！AI不能自己发明字段，不能自己写SQL，不能自己编关系，系统不认。

## 举两个真实例子，看完你就彻底懂了

### 例子1：算订单总金额（聚合查询）

**问题**："已支付并且金额大于等于一万元的订单，总金额是多少？"

**理想中的工单**：
```json
{
  "intent": "aggregate",           // 我要做聚合计算
  "object_types": ["order"],       // 查订单表
  "filters": [                     // 两个筛选条件
    {"field": "order.status", "operator": "eq", "value": "paid"},
    {"field": "order.amount", "operator": "gte", "value": 10000}
  ],
  "aggregates": [                  // 对金额求和
    {"function": "sum", "field": "order.amount", "alias": "total_amount"}
  ],
  "limit": 10
}
```

**执行过程**：
1. 代码检查：order表存在吗？status字段存在吗？amount字段是数字吗？gte（大于等于）是允许的操作符吗？sum是允许的聚合函数吗？→ 都合法
2. 筛选出所有status=paid且amount≥10000的订单
3. 把这些订单的amount加起来，得到总和
4. 把总和和参与计算的每个订单都作为证据返回
5. AI把结果写成自然语言："符合条件的订单总金额是XXX元，共X笔订单..."

**现在的状态**：
- ✅ 如果你手动把这张工单提交给执行器，能100%正确算出来
- ✅ 配了LLM之后，LLM能生成这样的工单，校验后执行
- ⚠️ 没配LLM的时候，默认的简单规则规划器很笨：它只能认出"订单"和"这是个统计问题"，默认给你算count（数个数），不能可靠认出"已支付"、"10000"、"求和金额"这些细节

---

### 例子2：找订单对应的客户（关系跳转查询）

**问题**："ORD-001这笔订单是哪个客户下的？"

**理想中的工单**：
```json
{
  "intent": "traverse",            // 我要跳关系查
  "object_types": ["order"],       // 从订单开始
  "filters": [
    {"field": "order.order_id", "operator": "eq", "value": "ORD-001"}  // 找到ORD-001这个订单
  ],
  "traversals": [
    {"relation": "placed_by", "direction": "out", "max_hops": 1}  // 沿"下单"关系向外跳1跳，找到客户
  ],
  "limit": 10
}
```

**执行过程**：
1. 检查：order表存在，order_id字段存在，placed_by关系存在吗？→ 合法
2. 找到order_id=ORD-001的订单
3. 沿placed_by关系跳1跳，找到下单的客户
4. 返回订单信息+客户信息+它们之间的关系证据
5. AI回答："ORD-001是张三（客户ID CUS-007）下的..."

**现在的状态**：
- ✅ 手动提交工单能100%正确执行，关系不存在会直接拒绝
- ⚠️ 没配LLM时，规则规划器不能稳定从话里提取出"ORD-001"这个编号，也不能稳定判断要跳哪条关系、往哪个方向跳

## 重点澄清："QueryPlan准确率1.000"到底是什么意思？别吹错了！

文档里说130道测试题准确率1.000，你千万别直接写"QueryPlan准确率100%"在简历上，会被面试官问穿！

这个1.000的真实含义是：
> **给我正确写好的QueryPlan工单，我执行起来100%正确。**

测试的时候，是人工把130张正确工单（70道关系查询+60道过滤聚合查询）喂给执行器，执行器全部执行对了，所以是1.000。

它**不代表**：用户随便说一句话，AI都能100%生成正确的工单。这部分还需要接真实LLM，做自然语言到工单的评测，现在还没做这部分测试。

这就像：计算器100%算对加减乘除，但你让小学生念题目，他不一定能正确把算式按进计算器里。现在我们计算器（执行器）做完了，而且算得很准；但"把人话正确翻译成算式"（自然语言规划）这部分，简单规则版的"小学生"还很笨，需要接LLM这个"大学生"来做，还要考试看准确率。

**面试怎么说才准确**：
"我们实现了确定性QueryPlan执行器，对于符合Schema约束的结构化查询计划，在130道多跳和聚合测试题上执行准确率达到100%；自然语言到计划的生成我们采用LLM+白名单校验的方案，这部分的准确率评测正在进行中。"

这样说既讲了亮点，又实事求是，不会被问倒。

## 你怎么自己亲自试QueryPlan？

启动后端之后，打开Swagger文档：`http://127.0.0.1:8000/docs`

有三个接口可以玩：

| 接口 | 干什么 |
|------|--------|
| `POST /api/v1/networks/{network_id}/query-plans/preview` | 输入一句问题，只生成工单给你看，不执行，先看看计划对不对 |
| `POST /api/v1/networks/{network_id}/query-plans/execute` | 你自己写一张JSON工单，提交给执行器直接执行，测执行器准不准 |
| `POST /api/v1/networks/{network_id}/ask-planned` | 一步到位：生成工单→执行→返回答案+证据 |

建议你先拿preview接口玩，看看没配LLM的时候规则规划器生成的工单是什么样的，你就知道它现在有多"笨"了，配了LLM之后会好很多。

## 面试怎么讲QueryPlan这个亮点？

面试官问"你这个RAG和普通RAG有什么不一样？"，你可以这么说：

"普通RAG一般是用户提问→检索TopK文档块→丢给LLM生成回答，这种方式有几个问题：一是多跳关联和数值计算容易错，LLM经常算错数、找错关联；二是上下文里有很多无关内容，浪费Token；三是没有约束，LLM可能编造不存在的字段或关系。

我们做了QueryPlan结构化查询层：用户问题先由LLM生成受BKN Schema严格约束的结构化查询计划，所有对象、字段、关系、操作符都要通过白名单校验，校验不通过的计划会被打回，不会执行。校验通过后由确定性执行器完成过滤、多跳关系遍历、聚合统计，所有计算都是代码硬算，LLM只负责最后把结果组织成自然语言。

这样设计的好处：一是数值计算和关系查找100%准确，不会出现LLM算错数的问题，我们在130道多跳和聚合测试题上执行准确率是100%；二是上下文只包含相关证据，Token消耗更低；三是从架构上杜绝了SQL注入和LLM编造信息的问题，因为执行计划是白名单约束的，LLM不能执行任意代码。当然，自然语言到计划的生成准确率我们还在优化，通过评测集持续迭代。"
