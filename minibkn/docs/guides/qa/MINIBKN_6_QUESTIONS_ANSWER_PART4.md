## 问题1：MCP工具中，search_knowledge和ask_knowledge的区别是什么？

我直接给你对比两个工具的输入输出和内部流程，一目了然：

| 维度 | search_knowledge | ask_knowledge |
|------|------------------|---------------|
| **输入** | network_id, query, limit(可选，默认10) | network_id, question |
| **返回内容** | 纯SearchHit列表（只有检索结果，包含文档内容、分数、排名） | 完整AskResult：answer（自然语言回答）+ context（完整三层上下文+子图）+ citations（引用来源列表） |
| **内部执行流程** | 1. 读所有search_documents<br>2. 混合检索排序<br>3. 返回Top N结果，结束 | 1. 先调用search取Top20<br>2. 按level分组截断（schema≤5, instances≤8, actions≤5）<br>3. 用instances做种子，1跳BFS扩展子图<br>4. （当前硬编码）生成抽取式回答<br>5. 组装完整上下文+引用，返回 |
| **是否做子图扩展** | ❌ 不做，只返回直接命中的文档 | ✅ 做，返回完整关联子图 |
| **是否生成自然回答** | ❌ 不生成，只返回检索结果原样 | ✅ 生成回答（当前是硬编码，未来接LLM） |
| **Token消耗** | 少，只有检索结果 | 多，包含完整三层上下文+子图+回答 |
| **适用场景** | 1. AI想自己处理检索结果<br>2. 轻量搜索，不需要完整回答<br>3. 调试检索效果 | 1. 用户直接问业务问题，要完整答案<br>2. 需要引用来源和证据<br>3. 要关联对象一起返回 |

### 举个例子：问"哪些物料库存不够"

**search_knowledge返回的是（简化）：**
```json
[
  {
    "document": {
      "level": "instance",
      "entity_type": "material",
      "entity_id": "MAT-001",
      "title": "温度传感器",
      "content": "material 温度传感器 MAT-001 current_stock 8 ...",
      "citation": "resource://materials_csv#row=2"
    },
    "score": 0.0312,
    "bm25_rank": 1,
    "vector_rank": 2
  },
  ...其他7个结果
]
```
就是纯检索结果列表，没有关联供应商，没有回答，没有上下文组装。

**ask_knowledge返回的是（简化）：**
```json
{
  "question": "哪些物料库存不够",
  "answer": "库存低于安全库存的物料有：温度传感器（MAT-001...）；继电器模块（MAT-003...）",
  "context": {
    "schema": [/* 5条Schema定义 */],
    "instances": [/* 8条命中的实例，3个物料 */],
    "subgraph": {
      "nodes": [/* 3个物料 + 1个供应商，共4个完整对象，带所有属性 */],
      "edges": [/* 2条供应关系边 */]
    },
    "actions": [/* 1个创建补货预警动作 */]
  },
  "citations": ["bkn://...", "resource://...", ...]
}
```

简单说：**search是"帮我搜一下相关内容"，ask是"帮我回答这个问题，给我完整答案和证据"**。AI可以根据场景自己选：如果只是探索性搜索用search，如果要直接回答用户问题用ask。

## 问题2：自动生成Schema的时候到底会生成哪些东西？能否给个运行例子？display_name是什么意思？AI负责生成关系吗？

我给你从输入到输出完整走一遍自动生成流程，用供应链CSV当例子，100%按代码来。

### 先纠正一个误解：**关系当前也是纯规则生成的，AI不生成关系，AI只补描述！**

AI不会"创造"关系，关系还是按xxx_id匹配主键的规则自动生成，AI只是给生成好的对象和关系补自然语言描述而已。

---

### 自动Schema生成完整例子：

#### 输入：CSV文件

假设你导入了两个CSV：

`materials.csv`:
| sku | name | current_stock | safety_stock | unit_cost | supplier_id |
|-----|------|---------------|--------------|-----------|-------------|
| MAT-001 | 温度传感器 | 8 | 30 | 42.5 | SUP-001 |
| MAT-002 | 电容 | 120 | 50 | 2.5 | SUP-002 |
| MAT-003 | 继电器模块 | 4 | 25 | 18.8 | SUP-001 |

`suppliers.csv`:
| supplier_id | name | contact_person | phone |
|-------------|------|----------------|-------|
| SUP-001 | Precision Components | 张工 | 138xxxxxxx |
| SUP-002 | Quality Parts | 李工 | 139xxxxxxx |

---

#### 第一步：discover_source（纯规则，不用AI）

系统发现两个资源：
1. `materials_csv`：6个字段，3行数据
2. `suppliers_csv`：4个字段，2行数据

主键识别（按规则）：
- materials.csv：`sku`字段，名字是sku，非空，唯一 → 主键是sku
- suppliers.csv：`supplier_id`字段，名字以_id结尾，非空，唯一 → 主键是supplier_id

---

#### 第二步：_object_type() 为每个表生成ObjectType（纯规则，不用AI）

对materials_csv生成的ObjectType大概是这样：
```python
ObjectType(
    id="material",                           # 表名去复数、去_csv后缀
    name="Material",                         # 下划线转空格，首字母大写
    description="Generated from resource materials.csv",  # 默认描述，很简陋
    properties=[
        DataProperty(
            name="sku",
            display_name="Sku",              # 字段名转显示名
            value_type="string",
            description="",                  # 空的，等AI补
            mapped_field="sku"
        ),
        DataProperty(
            name="current_stock",
            display_name="Current Stock",
            value_type="integer",
            description="",
            mapped_field="current_stock"
        ),
        # ... 其他字段同理
    ],
    primary_keys=["sku"],
    display_key="name",                      # 因为有name字段，用name当显示名
    data_source=DataSourceBinding(
        source_type="resource",
        source_id="materials_csv",
        name="materials.csv"
    ),
    source_path="generated://resource/materials_csv"
)
```

同理，suppliers_csv生成id为`supplier`的ObjectType，主键是supplier_id，display_key是name。

---

#### 第三步：_relations() 自动发现关系（纯规则，不用AI）

遍历每个对象的每个字段，找以_id结尾的：
1. material对象有个字段叫supplier_id
2. 检查：有没有另一个对象的主键是supplier_id？
3. 找到了！supplier对象的主键就是supplier_id
4. 自动生成一个RelationType：

```python
RelationType(
    id="material_to_supplier",
    name="Material To Supplier",
    description="Generated by matching foreign key supplier_id",  # 默认描述
    endpoint=RelationEndpoint(
        source_object_type="material",
        target_object_type="supplier"
    ),
    mappings=[
        RelationMapping(
            source_property="supplier_id",
            target_property="supplier_id"
        )
    ],
    source_path="generated://relation/material_to_supplier"
)
```

**到这一步为止，完全不用AI，纯规则就生成好了两个对象+一条关系。**

---

#### 第四步：可选AI增强（use_ai=True才做）

如果开了AI增强，会把上面生成的objects和relations发给LLM，让它返回更好的描述：
```json
{
  "object_descriptions": {
    "material": "物料对象，存储物料的基本信息、库存水平、单价以及关联的供应商",
    "supplier": "供应商对象，存储供应商的基本信息、联系人及联系方式"
  },
  "relation_descriptions": {
    "material_to_supplier": "物料由供应商供应关系，表示某个物料是由哪个供应商提供的"
  }
}
```

然后代码把这些描述替换掉原来的"Generated from..."默认描述，仅此而已。

AI不会新增字段、不会改主键外键、不会改映射，只润色描述。

---

#### 什么是display_name？

display_name就是"给人看的名字"，对应代码里的字段：
- ObjectType有display_key：指定哪个字段作为对象的"显示名"，比如物料用name字段显示，显示出来就是"温度传感器"而不是"MAT-001"
- DataProperty有display_name：字段的显示名，比如current_stock显示成"Current Stock"或者"当前库存"，而不是直接显示字段名
- ObjectInstance有display_name：实例的显示名，就是display_key对应字段的值

**为什么需要display_name？** 因为数据库字段名一般是英文下划线命名（current_stock），给用户看或者给LLM看的时候，用自然语言的显示名更容易理解。比如：
- 原始字段名：`current_stock` → display_name：`当前库存`
- 原始实例ID：`MAT-001` → display_name：`温度传感器`

这样不管是界面展示还是给LLM的上下文，都用人类易读的名字，而不是干巴巴的ID。

看代码`graph_service.py`第151行：
```python
display_name = str(properties.get(object_type.display_key) or instance_id)
```
就是说，优先用display_key指定的字段值当显示名，如果没有就用instance_id（主键值）。

**面试可以这么讲**："我们的自动Schema生成采用规则优先的策略：表转对象、字段转属性、主键外键识别、关系发现全部由确定性规则完成，保证结构准确；AI只负责补充自然语言描述，不触碰核心结构，既降低了人工建模成本，又避免了AI生成结构的不可靠性。"

## 问题3：后续在表格识别、生成Schema方面，AI具体可以有哪些帮助？

当前AI只用得很浅，未来可以在这些环节引入AI，提升易用性，我按优先级排：

| 优先级 | 环节 | AI可以做什么 | 价值 |
|--------|------|--------------|------|
| P0 | **主键识别兜底** | 当规则不确定哪个是主键（比如有多个字段都满足非空唯一，名字都不像id），让LLM根据字段名和样例值判断哪个更像主键 | 提升主键识别准确率，减少手动调整 |
| P0 | **字段名不匹配的外键发现** | 规则只能发现xxx_id对应同名主键，AI可以识别：`vdr_code`对应`supplier_id`，`cust_no`对应`customer_id`这种名字不一样但语义是外键的情况，推荐候选关系，人确认后生效 | 解决自动关系发现的最大痛点，不用手动写关系BKN |
| P0 | **字段描述补全** | 根据字段名和样例值，自动生成每个字段的自然语言描述（当前只补了对象和关系的，没补字段的） | 提升Schema可读性，LLM回答时也更理解字段含义 |
| P1 | **字段语义类型识别** | 识别字段的业务含义：这是邮箱？电话？地址？金额？日期？百分比？而不是只靠值类型判断integer/string | 方便后续做自动校验、可视化、风控规则推荐 |
| P1 | **display_name中文化** | 把英文下划线字段名自动转成通顺的中文显示名，比如`current_stock`→`当前库存`，`contact_person`→`联系人` | 不用手动一个个写显示名 |
| P1 | **推荐动作和风控规则** | 根据对象和字段，自动推荐可能的业务动作和风控规则，比如识别到有库存字段就推荐"创建补货预警"动作，识别到金额字段就推荐"金额阈值审批"风控规则，人确认后生成BKN | 大幅降低建模门槛，上传数据就能得到可用的Schema |
| P2 | **自然语言交互式建模** | 用户用自然语言说"我想加一个客户和订单的关系，一个客户可以有多个订单，通过customer_id关联"，AI自动转成RelationType定义 | 完全不用懂BKN格式，会说话就能建模 |
| P2 | **脏数据识别和清洗建议** | AI看样例数据，发现异常值、格式不统一、缺失值等问题，给出清洗建议 | 提升数据质量 |

### 核心原则：AI只做"推荐"，人做"确认"

不管AI推荐什么，核心结构（主键、外键、关系、字段映射）必须经过人确认后才生效，AI不能直接改Schema，避免幻觉导致结构错误。这是企业系统的安全要求。

## 问题4：至多8个实例被检索出来，然后去关系库找只要两边有一个在集合里就加进来，最后返回集合里所有元素的完整属性+关系边，这样理解对吗？

**完全正确！你的理解100%准确，我给你再确认几个细节，你就彻底懂了：**

你的理解拆解：
1. ✅ 检索Top20，取前8个instance类型的结果作为种子
2. ✅ 遍历关系表（relation_instances）所有边
3. ✅ 只要边的source或者target任意一端在种子集合里，就把另一端也加进集合
4. ✅ 最后集合里所有对象（原始8个+扩展出来的），每个都带完整properties属性
5. ✅ 所有两端都在集合里的边，作为edges返回

我给你补两个代码里的细节：

### 细节1：当前代码只做1跳扩展，不会递归扩展2跳、3跳

看`retrieval_service.py`的`_context_subgraph()`（第98-117行），只遍历了一次边，扩展一层就停了：
```python
for edge in all_relations:
    source = ...
    target = ...
    if source in selected or target in selected:
        selected.update((source, target))
```
没有循环，没有递归，所以是严格的1跳扩展，不会"朋友的朋友也加进来"。

（注意：独立的`/subgraph`API支持1-5跳深度，就是`graph_service.py`第75-106行那个，有个for循环做depth次扩展，但ask接口里调用的_context_subgraph是固定1跳的。）

### 细节2：如果两个种子对象之间有关系，这条边也会返回

比如检索命中了MAT-001和MAT-003两个物料，它们都关联SUP-001，那么：
- MAT-001→SUP-001这条边会返回
- MAT-003→SUP-001这条边也会返回
- 不会因为MAT-001和MAT-003都是种子就漏掉它们和SUP-001的边

### 细节3：扩展来的对象不会再继续扩展

比如：物料→供应商，供应商如果还有上级经销商（supplier.parent_supplier_id），当前1跳扩展只会拉到供应商，不会再拉供应商的上级经销商，因为只遍历一次边。如果要拉上级，需要多跳，ask接口当前没开。

### 问题5.2：bkn_document更新删除后如何同步？

当前MVP版本**没有增量更新机制**，是全量替换模式：

1. 你修改了BKN文件，调用`/api/v1/networks/import`重新导入整个目录
2. 代码里`save`方法（repository.py第34-62行）会：
   - 更新knowledge_networks表的payload为新的完整JSON
   - 先**删除**这个network_id下所有旧的bkn_documents（第57-59行：`delete(BknDocumentRow).where(BknDocumentRow.network_id == network_id)`）
   - 再重新插入所有新的bkn_documents
3. 导入新Schema后，需要重新调用materialize物化数据（因为字段映射可能变了）
4. 然后重新调用build_index重建search_documents索引

就是说：**改Schema → 重新import → 重新materialize → 重新build_index**，全量重新来，简单粗暴，不会出错。

未来如果要做增量更新：
- 可以基于bkn_documents表，单独更新某一个文档，不用全量替换
- 更新后只需要重新物化受影响的对象类型，重建受影响的索引
- 但MVP阶段全量重建简单可靠，数据量小的话（几千几万条数据）全量重建也就几秒钟，完全够用

## 问题6：object_instances/relation_instances和search_documents内容完全相同吗？search_documents只是前面两个复制一份用于检索吗？

**不，它们内容不一样，也不是简单复制，我给你对比一下就清楚了：**

### 先看字段对比：

| 字段 | object_instances | search_documents(instance类型) |
|------|------------------|--------------------------------|
| 定位字段 | network_id, object_type_id, instance_id | network_id, level, entity_type, entity_id |
| 显示字段 | display_name, resource_id, row_number | title, citation |
| **核心内容** | properties: JSON字典，结构化的键值对<br>例：`{"sku": "MAT-001", "current_stock": 8, ...}` | content: 字符串，所有key value拼成空格分隔的纯文本<br>例：`"material 温度传感器 sku MAT-001 current_stock 8 safety_stock 30 ..."` |
| 向量字段 | ❌ 没有 | ✅ vector: 预计算好的嵌入向量 |
| 其他字段 | - | bm25需要的词频等信息（当前存在内存里，不存表） |

### 本质区别：

1. **存储目的不同**：
   - object_instances/relation_instances是**结构化权威数据源**：存的是正常的键值对，方便按字段查询、做关系匹配、做计算、绑定参数
   - search_documents是**检索优化的非结构化读模型**：把所有信息拼成一大段文本，预计算好向量，专门给BM25和向量检索用，不适合做结构化查询

2. **包含范围不同**：
   - object_instances/relation_instances只有实例数据和关系
   - search_documents包含三种内容：Schema文档、实例文档、动作文档，后两者来自object_instances和action定义，Schema文档来自BKN定义，object_instances里没有Schema和动作

3. **数据形式不同**：
   - object_instances里properties是结构化的，可以直接拿`current_stock`的值做计算（比如判断<safety_stock，算补货金额）
   - search_documents里content是纯文本，你没法直接从文本里拿出current_stock的值做计算，必须回到object_instances里拿结构化数据

### 举个MAT-001的例子对比：

**存在object_instances里的内容**（结构化）：
```python
ObjectInstance(
    network_id="supply_chain_demo",
    object_type_id="material",
    instance_id="MAT-001",
    display_name="温度传感器",
    resource_id="materials_csv",
    row_number=2,
    properties={
        "sku": "MAT-001",
        "name": "温度传感器",
        "current_stock": 8,          # 整数，可以直接算
        "safety_stock": 30,         # 整数，可以直接算
        "unit_cost": 42.5,          # 浮点数，可以直接算
        "supplier_id": "SUP-001"
    }
)
```

**存在search_documents里的内容**（检索专用）：
```python
SearchDocument(
    id="instance:material:MAT-001",
    network_id="supply_chain_demo",
    level="instance",
    entity_type="material",
    entity_id="MAT-001",
    title="温度传感器",
    content="material 温度传感器 sku MAT-001 current_stock 8 safety_stock 30 unit_cost 42.5 supplier_id SUP-001",
    #       ^^^^^^^^ 纯文本，给分词和向量算相似度用
    citation="resource://materials_csv#row=2",
    vector=[0.023, -0.145, 0.087, ...]  # 预计算好的向量
)
```

### 检索完之后发生了什么？

1. 在search_documents里检索，找到相关的SearchDocument，得到entity_type和entity_id
2. 通过entity_type和entity_id，去object_instances里拿完整的结构化对象（带properties字典）
3. 用这些ID去relation_instances里找关联关系，做子图扩展
4. 把结构化对象组装成上下文给LLM，或者做规则计算

所以search_documents就像一本书的**索引卡片**，上面只有关键词和编号，帮你快速找到位置；object_instances才是**书的正文**，有完整内容。索引卡片是为了快速查找做的辅助，不能代替正文。

**不是简单复制，是针对检索场景做了格式转换和预计算（文本拼接+向量计算）的专门读模型。**

**面试可以这么讲**："我们采用读写分离的存储设计：对象和关系表作为权威结构化存储，保证数据一致性和查询计算能力；另外构建search_documents作为检索专用读模型，将Schema、实例、动作统一预拼接成文本并预计算向量，专门优化检索性能，这种CQRS风格的设计兼顾了数据一致性和检索效率。"
